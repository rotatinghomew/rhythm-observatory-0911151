# 本地资料与成果协议

资料服务是只读业务资料的边界，消费端负责当前资格及不可改写的成果保存。两者由同一开发服务进程提供独立 HTTP 接口，客户代码不直接连接它的数据库；线上可分别部署，产品算法不依赖端口和本地文件路径。

## 资料可见性

`GET /snapshot?as_of=2024-05-01` 返回公开日期不晚于指定日的资料。同一表中 `id` 是业务记录标识，`revision` 是修订代次；按公开日期和代次择最新记录，最新记录的 `withdrawn=true` 表示撤回，不能回退到更早值。业务期间与公开日期是两件事。快照有 `as_of`、`snapshot_id`、`tables`；指纹覆盖日期及完整可见记录。客户拿到的资料已完成版本选择，不应再把不同版本拼接。

`GET /policy` 返回消费约束与当前 `revision`。它不属于历史分析资料，提交操作总要服从当前消费约束；此前发布的成果仍按原样读取。

## 成果发布

`POST /artifacts` 的 JSON 包含 `request_key`、`policy_revision`、`artifact`。成果含 `as_of`、`snapshot_id`、`method`、`result`，可增加模型、配置和方法相关字段。若含 `items`，其中记录也受当前禁用列表限制。服务会重新计算该日期的资料指纹，但不会代替业务算法审查结论。浮点数必须有限；缺失信息用明确状态和 `null` 表达，不写 NaN 或 Infinity。

首次成功返回 201 和不可变 `artifact_id`。同一个请求键与相同内容重试返回同一成果；同键异内容为 409。新发布的消费约束代次过期、项目被禁用同样为 409。已有成果不会被重试、后续修订或约束更新覆盖。`GET /artifacts/编号` 返回原始成果，缺失编号为 404。字段或指纹无效返回 400。

本地联调可用 `POST /policy`，JSON 含 `expected_revision` 和 `policy`，按比较交换更新消费约束。此接口仅用于本地管理，不是分析方法输入。`GET /health` 返回产品名与状态。错误响应均含中文 `error`，客户端保留 HTTP 状态以区分无效请求与冲突。
